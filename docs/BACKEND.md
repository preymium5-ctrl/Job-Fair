# Recruitment backend

The Node.js route handlers use the same typed Drizzle schema with PostgreSQL in production and a durable PGlite database in local mode. Jobs, submitted applications, staff credentials, sessions, rate limits, and audit events are persisted. No external service is reported as connected until its supplied configuration has been tested.

## Local use

1. Copy `.env.example` to `.env.local` and retain `CHAPTER_LOCAL_MODE=true`.
2. Run `npm install` and `npm run admin:setup -- --email you@example.com`. The script prompts for a password of at least 12 characters without displaying it. There is no default account.
3. Run `npm run dev` and sign in at `/admin`.

PGlite stores data at `.data/db`; private files live under `.data/uploads`, outside `public`. Its local database is for **one Node.js process at a time**. Stop the web server before running `admin:setup` against the same local database. Local example jobs seed once; edits survive restarts. Do not remove `.data` to restart the site unless you intend to delete its data. `.data`, private environment files and generated QA assets are excluded from Git.

For a built local preview, explicitly set `CHAPTER_LOCAL_MODE=true` when running `npm run build` / `npm start`. This is a local preview setting and must be removed from a real deployment. `DATA_DIR` can select a persistent directory. Back up the full database and uploads together while the local process is stopped.

The setup script accepts `ADMIN_SETUP_EMAIL` and `ADMIN_SETUP_PASSWORD` environment variables for non-interactive provisioning. Remove the password variable afterward. To reset an existing staff member's password, run `npm run admin:setup -- --email you@example.com --reset`; it revokes all their sessions. Run this command only from an authorized server shell.

## Production configuration

Use a Node.js deployment with `DATABASE_URL`, `APP_ORIGIN`, `SESSION_SECRET`, `S3_BUCKET`, `S3_REGION`, `S3_ACCESS_KEY_ID`, and `S3_SECRET_ACCESS_KEY`. Generate a random session secret, serve over HTTPS, provision a real administrator, and keep the S3-compatible bucket private. Compatible storage may also require `S3_ENDPOINT` and `S3_FORCE_PATH_STYLE`. Database migrations initialize automatically on the first database connection under a PostgreSQL advisory lock; the deployment database role needs the privileges to create these tables and indexes.

Production application and staff routes reject a missing database, a missing or short session secret, unconfigured private storage, or production applications without a provisioned administrator. Public pages can use the source-controlled catalog without a database. Database-backed production starts with no jobs unless `SEED_PROPOSED_JOBS=true` is explicitly chosen to import and migrate the catalogue (`SEED_EXAMPLE_JOBS=true` remains a legacy alias). The catalogue contains 17 grouped roles with 11,100 current displayed slots; the PDF's original 248 workers remain archived source figures. Salary amounts are proposed NET EUR per month, not confirmed employer offers. The versioned update closes only the 12 original seed IDs and archives their slugs while preserving IDs, applications, audit history, and custom staff records. Any slug conflict with a custom record rolls back the transaction. The persistent version marker preserves later staff edits across restarts. Real vacancies and employment terms must be supplied and verified by the operator.

The 20 October employer-position expansion has been rolled back. A new versioned migration closes its six added canonical listings without deleting records or applications and restores four grouped slot totals only when the split values are unchanged. Staff counts, renamed records, custom jobs and closed statuses are retained. Historical queued applications for the retired listings keep their employer and NC2 context on Google Sheets retries. Fresh databases seed only the original 17 roles.

Set `TRUST_PROXY=true` only if the deployment's trusted reverse proxy overwrites `X-Forwarded-For` with the client's address. Otherwise rate limiting deliberately uses a shared request bucket. Limits persist in the database, including across multiple PostgreSQL instances of the application. Apply your production retention, access-review and backup policy to applications, resumes, audit events and expired sessions; this implementation does not impose an invented business retention period.

External PostgreSQL and S3 credentials were unavailable during implementation, so the external deployment path has not been integration-tested. Automated tests exercise local durable persistence and the API security behavior.

## API contracts

Public `POST /api/applications` accepts multipart fields `payload` (JSON matching `ApplicationInput`), `resume` (File), `website` (empty honeypot) and `idempotencyKey` (UUID). Supporting files use `document:passport`, `document:residence-id`, `document:diploma`, `document:employment-certificate`, `document:nc2`, `document:nbi`, `document:form18a`, `document:other` and `document:driver-license`, one per category. Applications with the new `profile` object require passport and residence ID files as well as the CV; driver applicants also require a driver's license copy. Legacy requests without a profile retain their original optional-document behavior. Diploma, NC2, NBI clearance with apostille and Form 18a may be required for work permits but remain optional uploads at the application stage; Form 18a is identified for Croatia applicants. Missing, duplicate or invalid supporting files return category-specific errors such as `document:passport`. Profile applications may include optional driver-license details and a copy for other jobs; legacy requests without a profile retain the restriction to the 17 PDF roles. Unknown or duplicate file fields are rejected. It returns `{ reference, jobTitle }` only after the application and all private files have been persisted. Repeating the same submission key and content returns the same reference; different content, including changed attachments, is rejected. Failed persistence triggers cleanup of all staged files.

The optional `ApplicationInput.profile` preserves older records and clients. When supplied it contains required first/last names, gender, address, date/place of birth, destination country, current work country, second job choice, English-language response and accepted terms, plus optional Telegram contact, parents' names and another job choice. Nationality is no longer collected; its optional field remains supported for older records. Destination choices include Croatia, Slovenia, Serbia, Romania, Macedonia and Montenegro; historical `North Macedonia` answers remain accepted. The server checks that the full name matches the two name fields, dates are real calendar dates before the current UTC day, enum answers are valid and terms are accepted. Gender, date of birth and the English response do not create eligibility filters. Profile fields are bounded and the applicant's professional summary is limited to 1,000 characters for profile submissions (legacy requests retain 4,000). Profiles are stored in the existing application JSONB record and shown to authorized staff; no database migration is needed.

The reference form does not ask for country of residence, most recent role, years of experience or a separate skills statement. Profile requests may omit those legacy fields: `country` defaults to the answered current-work-country field, recent role/skills default to empty strings and experience defaults to `null`. Staff sees **Not collected** for unanswered background fields. No job title, skill or experience total is inferred from the chosen vacancy. Legacy requests without a profile retain their required background answers and minimum three years of relevant experience. The Google receiver accepts null experience and writes a blank experience cell. Expanded profile exports require its schema-5 source and 54-column header migration; older version-1 and version-2 payloads remain supported, including the shared Jobstreet Croatia sender. See [Google Sheets setup](GOOGLE_SHEETS_SETUP.md) for deployment and compatibility checks.

Profile submissions cap CVs at 3 MiB and combined uploads at 4 MiB, leaving room for multipart fields within the deployed provider's request-size limit. Legacy submissions without a profile retain the 5 MiB CV and 15 MiB combined limits. CVs are restricted to PDF, DOC and DOCX. The server checks actual signatures; DOC requires Word compound-document markers, and DOCX requires coherent ZIP directories and Word XML, with expanded-size, encryption, macro and embedded-executable restrictions. Client MIME is not trusted for resumes. Resume downloads require staff authentication, are returned as attachments, have `no-store` headers, and create an audit event.

Staff API endpoints:

Supporting files accept PDF, DOC, DOCX, JPG and PNG up to 3 MiB each, subject to the combined 4 MiB profile or 15 MiB legacy limit including the CV. Images are decoded, rotated, stripped of metadata and re-encoded as JPEG. Document downloads use the same staff authentication, audit and private attachment headers as CV downloads. Version-3 Google payloads send structured profile answers and all supplied supporting categories, including passport, residence ID and employment certificates, for private Drive storage. The website retains its private copies for authorized recruitment downloads. The schema-5 receiver preserves the original A:AD columns and appends 20 profile-answer columns in AE:AX, the three new private document links in AY:BA and the submitting website in BB. Readable profile lines and document filenames remain in the professional-summary cell. Original supporting categories still export in W:AA, with driver license details in AB and a private license-copy link in AC. AD accepts both `referralSource` and Jobstreet Croatia's `discoverySource`, with either recognized source header. CV-only version-1 and supporting-file version-2 exports remain compatible. Document-readiness statuses are no longer collected by the form or written into the spreadsheet. Upgrading the receiver does not automatically backfill already synced applications. Immediate delivery is bounded to 20 seconds, while the background worker allows up to 120 seconds per request.

| Endpoint | Request | Result |
| --- | --- | --- |
| `/api/admin/session` | GET / POST `{email,password}` / DELETE | `{authenticated,email?}` |
| `/api/admin/jobs` | GET / POST full Job fields | `{jobs}` / `{job}` |
| `/api/admin/jobs/[id]` | PATCH job fields | `{job}` |
| `/api/admin/applications` | GET | `{applications}` |
| `/api/admin/applications/[id]` | PATCH `{status}` | `{application}` |
| `/api/admin/applications/[id]/resume` | GET | Private attachment |
| `/api/admin/applications/[id]/documents/[documentId]` | GET | Private supporting attachment |
| `/api/admin/images` | POST multipart `image` | `{url}` |

All mutations require a matching Origin header; production requires an explicit HTTPS `APP_ORIGIN`. Staff cookies are signed, HttpOnly, SameSite Strict, secure on production HTTPS, expire after eight hours, and are backed by revocable database sessions. Passwords use salted scrypt. Login and submission limits persist in the database. Job edits and application status changes are committed with audit records in the same transaction. Application references have a database uniqueness constraint. A job-row lock keeps an application insertion from racing a vacancy closure.

Job photos accept JPEG, PNG and WebP up to 8 MB / 36 million decoded pixels, at least 300 × 200. The server decodes, rotates and re-encodes them as JPEG, removes metadata, and caps the dimensions at 2000 × 2000. Only sanitized JPEG photo keys can be served through the public `/api/images/[key]` endpoint. Resume keys can never be served there.

API errors return `{error,fieldErrors?}` and never include database queries, applicant data, private file paths or credentials.

File signatures and archive restrictions are format validation, not malware detection. PDF and legacy DOC formats can contain active content that these checks do not fully parse. Resumes remain private and download as attachments; staff should inspect them using protected document tooling. An operator needing malware scanning should attach its approved scanner before publishing. This implementation includes no email delivery, external ATS integration or automatic retention deletion; the current workflow is the protected staff portal.

## Verification

`npm test` covers password/session integrity, validation, private storage, durable database restart, audited job edits, idempotent submission, rejection paths, authorized resume download, audited application status changes, logout revocation, persisted rate limits, and missing production configuration. Tests use isolated temporary data, not the developer's recruitment records.
